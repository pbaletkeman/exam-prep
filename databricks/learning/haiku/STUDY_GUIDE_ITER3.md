## Topic 1: Apache Spark Architecture & Internals (20% - Questions 1–20)

### 1.1 RDD vs DataFrame Lineage Storage

**RDD Lineage**:
- Chain of parent RDD dependencies
- Stored as a DAG of RDD transformations
- Lineage is retained in RDD's internal structure
- Recomputation follows the exact RDD transformation chain on failure

**DataFrame Lineage**:
- Stored as an **optimized logical plan**
- Passes through **Catalyst optimizer** before execution (analysis, optimization, physical planning)
- Logical operators (`Filter`, `Project`, `Join`, `Aggregate`) are optimized and rewritten
- Physical plan may differ significantly from the logical plan (e.g., join reordering by CBO)
- Advantages: More optimization opportunities, better visibility into execution strategy

**Key Insight**: DataFrames have higher abstraction and optimizer leverage compared to RDDs.

### 1.2 Whole-Stage Code Generation (WholeStageCodegen)

**What It Does**:
- Fuses multiple operators (filter, project, aggregate) in a pipeline stage into a **single optimized JVM bytecode function**
- Eliminates virtual function call dispatch overhead between operators
- Generates dynamically during physical planning

**Example Fusion**:
```
Filter → Project → Aggregate → Single generated bytecode function
```

**Execution Model**:
- In physical plans, you see `*(1)`, `*(2)`, etc. indicating WholeStageCodegen units
- Each unit is a separate generated class
- One unit per sub-plan that can be fused

**Performance Benefit**: 10–100× faster for pipeline-heavy queries (e.g., filters + projections + aggregations on large datasets) by reducing per-row overhead.

### 1.3 Tungsten Project

**Focus**: CPU and memory efficiency improvements

**Key Optimizations**:
- **Binary Data Encoding**: Compact off-heap or managed memory format (not Java objects)
- **Cache-Aware Computation**: Data layout optimized for CPU cache efficiency
- **Runtime Code Generation**: JVM bytecode generation at runtime (WholeStageCodegen)
- **Direct Memory Management**: Reduces GC pressure by using off-heap memory for Spark's own data structures

**Impact**: Dramatic reductions in memory usage (5–10× less than object-based) and improved CPU cache hit rates.

### 1.4 External Shuffle Service

**Purpose**: Persist shuffle intermediate files on worker nodes independent of Executor lifetime

**Key Benefit**: Enables **Dynamic Resource Allocation (DRA)**
- When an Executor is removed (due to idle timeout), its shuffle output files are NOT lost
- Downstream Executors can still fetch the shuffle files from the external shuffle service
- Without external shuffle service, removing an Executor would lose its shuffle outputs and force recomputation

**Architecture**:
- Separate service running on each worker node (not inside Executor JVM)
- Executors write shuffle blocks to the external shuffle service
- Executors fetch from the external shuffle service, not directly from other Executors

### 1.5 Checkpoint vs Persist

**`persist()`**:
- Caches DataFrame in memory/disk within the Executor
- Lineage is **retained**; on Executor failure, lineage is used to recompute
- Lazy operation; data materialization happens on first action

**`checkpoint()`**:
- Writes DataFrame to **reliable distributed storage** (HDFS, S3, cloud storage, etc.)
- Configured via `spark.sparkContext.setCheckpointDir(path)`
- **Truncates the lineage graph**; recomputation on failure starts from checkpoint, not from the original source
- Cuts off lineage chain to break long dependency graphs (avoids stack overflow, speeds up recomputation)

**When to Use**:
- `persist()`: Short-term caching within a query
- `checkpoint()`: Breaking very long lineages (100+ transformations); breaking lineage before iterative algorithms

### 1.6 Task Serialization & Closures

**What Gets Serialized**:
1. The function/closure to execute (e.g., the lambda in `map()`)
2. All variables **captured** by the closure that are referenced in the function
3. Class references and configuration needed by the function

**Serialization Mechanism**:
- **Default**: Java serialization (works but slow and large)
- **Kryo**: Faster and more compact alternative

**Common Mistake**: Accidentally capturing large objects in closures
```python
# BAD: Captures entire 'df' object
df = spark.read.parquet(...)
rdd = df.rdd
rdd.map(lambda row: process_using(row, df))  # 'df' is captured!

# GOOD: Use only what's needed
rdd.map(lambda row: row.value * 2)
```

### 1.7 Kryo Serialization

**Why Kryo?**:
- **Faster** than Java serialization (binary format, minimal overhead)
- **More compact** (smaller serialized size)
- Recommended for performance-critical applications

**Configuration**:
```python
spark.conf.set('spark.serializer', 'org.apache.spark.serializer.KryoSerializer')
```

**When to Use**:
- Performance-sensitive jobs with high RDD usage
- Large closure objects being serialized repeatedly
- Not required for DataFrames (though still beneficial)

### 1.8 Off-Heap Memory for Tungsten

**Configuration** (both required):
```python
spark.memory.offHeap.enabled = true        # Enable off-heap
spark.memory.offHeap.size = "2g"           # Size allocation
```

**What It Provides**:
- Off-heap memory region for Tungsten data structures
- Reduces JVM heap pressure
- Improves GC performance (less GC pause time)

**Where It's Used**:
- Shuffle buffers
- Broadcast variables
- Cached data blocks (when using off-heap storage level)

### 1.9 Python Worker Processes in PySpark

**Architecture**:
1. Executor JVM receives a Task with Python code
2. JVM spawns a separate **Python worker process** (one per Executor thread)
3. JVM serializes input data (pickled) and sends to Python process via socket
4. Python process executes UDF on data
5. Python process serializes output and sends back to JVM
6. JVM deserializes result and continues

**Memory Implications**:
- Python process memory is **outside the JVM heap**
- Configured by `spark.executor.memoryOverhead` and `spark.executor.pyspark.memory`
- PySpark jobs require more memory overhead than Scala/Java jobs

### 1.10 Cluster Manager Comparison

| Manager | Master Service | Port | Worker Service | Deploy Modes | Notes |
|---------|---|---|---|---|---|
| **Standalone** | `spark-master` | 7077 | `spark-worker` | Client, Cluster | Simple; no dependencies; Master tracks available workers |
| **YARN** | ResourceManager | 8088 | NodeManager | Client, Cluster | Hadoop integration; fine-grained resource management |

### 1.11 Data Locality Levels (in Execution Order)

| Level | Meaning | Speed |
|-------|---------|-------|
| `PROCESS_LOCAL` | Data is in the **same JVM process** as the Executor running the Task | Fastest |
| `NODE_LOCAL` | Data is on the same physical machine (different process or disk) | Fast |
| `RACK_LOCAL` | Data is in the same rack | Medium |
| `ANY` | Data is anywhere in the cluster | Slowest |

**Spark's Scheduling Strategy**:
1. Try to schedule Task on PROCESS_LOCAL if possible
2. Fall back to NODE_LOCAL if PROCESS_LOCAL unavailable
3. Fall back to RACK_LOCAL if NODE_LOCAL unavailable
4. Finally, schedule on any available node

### 1.12 Resource Profile API (Spark 3.1+)

**Purpose**: Allow different stages within the same application to request different Executor configurations

**Configurability**:
- CPU cores per Executor
- Memory per Executor
- GPU/custom resources per Executor

**Usage**:
```python
from pyspark.resource import ResourceProfile
profile = ResourceProfile.builder() \
  .require(ResourceRequirement(CORES, '4')) \
  .require(ResourceRequirement(MEMORY, '2g')) \
  .build()

# Attach to RDD or DataFrame stage
rdd.withResources(profile)
```

### 1.13 Rack Awareness & Network Locality

**What Rack Awareness Does**:
- Scheduler has information about cluster network topology (which machines are in the same rack)
- When data is on machines in one rack but no local execution opportunity exists, the scheduler prefers RACK_LOCAL over ANY

**Impact**: Reduces cross-rack network traffic, improving overall cluster throughput

### 1.14 Speculative Execution

**Behavior**:
- Detects straggler Tasks (unusually slow relative to median)
- Launches duplicate copies on other Executors
- First copy to finish wins; others are killed

**Configuration**:
- `spark.speculation = true` — enable
- `spark.speculation.multiplier` — how many times slower than median before launching copy (default 1.5)
- `spark.speculation.quantile` — which quantile of task durations to use for comparison (default 0.75)

### 1.15 Unified Memory Model: Storage vs Execution Borrowing

**Memory Regions**:
```
Executor Heap (e.g., 8 GB)
  ├─ Spark Memory (60% by default = 4.8 GB)
  │  ├─ Storage Memory (initially ~2.4 GB)
  │  └─ Execution Memory (initially ~2.4 GB)
  ├─ User Memory (40% = 3.2 GB)
  └─ Reserved (~200 MB)
```

**Borrowing**:
- If Execution Memory needs more space and Storage has cached data, Spark **evicts** (spills) Storage blocks to free room
- If Storage Memory needs more space and Execution is idle, Spark can expand Storage into Execution region
- Improves utilization vs fixed-partition model

### 1.16 Shuffle Reduce-Side Memory

**`spark.reducer.maxSizeInFlight`**:
- Controls how much shuffle data a reducer-side Task fetches **concurrently** from remote Executors
- Default: 48 MB
- If set too high: OOM on Executor
- If set too low: More serialization/deserialization passes, slower performance

**`spark.shuffle.compress`**:
- Compresses shuffle output files on disk (default true)
- Uses `spark.io.compression.codec` (default `lz4`)
- Trades CPU for disk I/O reduction

## Topic 2: Spark SQL (20% - Questions 21–40)

### 2.1 Higher-Order Functions on Arrays

**`F.transform(array, lambda x: expression)`**:
- Applies transformation to each element
- Returns new array with transformed values

**`F.filter(array, lambda x: predicate)`**:
- Filters array elements matching predicate
- Returns filtered array

**`F.aggregate(array, initial, lambda acc, x: operation)`**:
- Reduces array to single value using accumulator
- Starts with `initial` value, applies operation cumulatively

**`F.flatten(array_of_arrays)`**:
- Concatenates nested arrays into single flat array
- Input: `ArrayType(ArrayType(T))`
- Output: `ArrayType(T)`

**`F.forall(array, lambda x: predicate)`** and **`F.exists(array, lambda x: predicate)`**:
- `forall`: Returns true if **all** elements satisfy predicate
- `exists`: Returns true if **at least one** element satisfies predicate
- Both return `BooleanType`

### 2.2 Higher-Order Functions on Maps

**`F.map_filter(map, lambda k, v: predicate)`**:
- Filters map entries where predicate returns true
- Returns new map with filtered key-value pairs

### 2.3 JSON & Schema Functions

**`F.from_json(col('json_string'), schema)`**:
- Parses JSON string column into Struct/Array according to schema
- Requires explicit schema definition

**`F.to_json(col('struct_col'))`**:
- Serializes struct/map/array to JSON string

**`F.schema_of_json('sample_json_string')`**:
- Returns a **DDL string** describing the inferred schema (e.g., `'STRUCT<id: BIGINT, name: STRING>'`)
- Useful for dynamic schema inference

### 2.4 String/Array/Map Manipulation

| Function | Behavior |
|----------|----------|
| `F.split(col, delimiter)` | String → `ArrayType(StringType)` |
| `F.explode(array)` | One row per element; drops null/empty |
| `F.posexplode(array)` | Like explode but adds `pos` column (0-based index) |
| `F.lpad(col, length, padding)` | Left-pad string to length |
| `F.rpad(col, length, padding)` | Right-pad string to length |
| `F.element_at(array, index)` | Array access using **1-based indexing** |
| `F.slice(array, start, length)` | Slice using **1-based indexing** |
| `F.array_union(a, b)` | Union of arrays (deduplicated) |
| `F.array_intersect(a, b)` | Intersection (deduplicated) |
| `F.array_except(a, b)` | Elements in `a` not in `b` (deduplicated) |
| `F.array_distinct(array)` | Remove duplicates from array |
| `F.arrays_zip(a, b)` | Zip two arrays into `ArrayType(StructType)` pairs |
| `F.zip_with(a, b, lambda x, y: expr)` | Element-wise operation on two arrays |
| `F.map_keys(map)` | Extract keys as array |
| `F.map_values(map)` | Extract values as array |

### 2.5 Date/Time Functions

| Function | Return Type | Behavior |
|----------|-------------|----------|
| `F.months_between(end, start)` | DoubleType | Fractional months between dates |
| `F.date_add(date, days)` | DateType | Add days to date |
| `F.datediff(end, start)` | IntegerType | Days between dates |
| `F.date_format(date, pattern)` | StringType | Format date as string |
| `F.to_timestamp(col, pattern)` | TimestampType | Parse string to timestamp with format |

### 2.6 Conditional Functions

| Function | Behavior |
|----------|----------|
| `F.greatest(col1, col2, ...)` | Maximum non-null value |
| `F.least(col1, col2, ...)` | Minimum non-null value |
| `F.when(condition, value)` | CASE WHEN; can chain with `.otherwise()` |
| `nvl(col, default)` | Return default if col is null |
| `nvl2(col, if_not_null, if_null)` | Return if_not_null if col is NOT null, else if_null |
| `try_cast(col, type)` | Cast with null on failure (no exception) |

### 2.7 SQL PIVOT Operation

**Purpose**: Rotate rows into columns

**Syntax**:
```python
df.groupBy('department').pivot('month', ['Jan', 'Feb', 'Mar']).agg(F.sum('amount'))
```

**SQL Equivalent**:
```sql
SELECT * FROM sales
PIVOT (SUM(amount) FOR month IN ('Jan', 'Feb', 'Mar'))
```

**Key Points**:
- Requires an aggregate function
- Pivot values can be hardcoded or dynamically determined
- Result columns named as pivot values

### 2.8 Window Functions: Advanced Cases

**`first(col, ignorenulls=True)` in Window Context**:
- Returns the first non-null value in the window frame
- `ignorenulls=False` (default) returns the first value regardless of null

**`LATERAL VIEW explode()`**:
- SQL syntax for exploding arrays in FROM clause
- Creates one row per element per original row

### 2.9 Optimizer Hints in SQL

**Broadcast Hint**:
```sql
SELECT /*+ BROADCAST(small_table) */ ...
FROM large_table a
JOIN small_table b ON ...
```

**Effect**: Forces optimizer to use BroadcastHashJoin for `small_table`, overriding the `autoBroadcastJoinThreshold`

## Topic 3: DataFrame API (30% - Questions 41–70)

### 3.1 DataFrame Summarization & Statistics

**`df.describe(cols)`**: Returns count, mean, stddev, min, max

**`df.summary()`**: Returns count, mean, stddev, min, **25%, 50%, 75%** (quartiles), max

**`df.stat.corr('col1', 'col2')`**: Pearson correlation coefficient (Python float)

**`df.stat.approxQuantile('col', [0.25, 0.5, 0.75], 0.05)`**: Approximate quantiles with error tolerance

**`df.stat.crosstab('col1', 'col2')`**: Contingency table (cross-tabulation); returns DataFrame with rows = distinct col1 values, columns = distinct col2 values, cells = counts

**`df.stat.freqItems(['col1', 'col2'], support=0.01)`**: Frequent items appearing in ≥1% of rows

### 3.2 DataFrame Operations & Utilities

**`df.limit(n)`**: First n rows (no ordering)

**`df.sample(fraction=0.1, withReplacement=False, seed=42)`**: Random sample

**`df.randomSplit([0.8, 0.2], seed=42)`**: Split into multiple DataFrames; actual split may not be exact

**`df.printSchema()`**: Print schema to console; returns None

**`df.hint('repartition', n)`**: Suggest to optimizer to repartition (not a guarantee)

**`df.transform(func)`**: Apply function to DataFrame for chaining (`func(df)` pattern)

### 3.3 Schema Operations

**`StructType.fromDDL('id BIGINT, name STRING')`**: Create schema from DDL string

**`StructField('name', StringType(), True)`**: Define nullable field

**`MapType(StringType(), DoubleType())`**: Key-value map schema

**`ArrayType(StringType())`**: Array schema

### 3.4 Advanced Write Operations

**`df.write.bucketBy(16, 'user_id').sortBy('event_time').saveAsTable('table')`**:
- Writes into 16 bucket files grouped by hash of `user_id`
- Sorts within each bucket by `event_time`
- Enables bucket join (eliminates shuffle if both tables are bucketed identically on the same key)

**`df.write.insertInto('table')`**:
- Matches columns **by position** (not by name!)
- Appends to existing table

**`df.writeTo('catalog.schema.table').append()`** (v2 API):
- More explicit table operations
- Supports `.replace()`, `.createOrReplace()`, `.overwritePartitions()`

**`df.write.format('parquet').save(path)`**: Generic write API

### 3.5 Checkpoint Operations

**`df.checkpoint()`**:
- Writes to reliable distributed storage
- Truncates lineage

**`df.localCheckpoint()`**:
- Writes to local Executor disk (fast but not fault-tolerant)
- Still truncates lineage

### 3.6 Array/Map Functions

**`F.create_map(key1, val1, key2, val2, ...)`**: Build map from alternating key-value expressions

**`F.element_at(array, index)`**: Access array element using **1-based indexing**

**`F.slice(array, start, length)`**: Extract slice using **1-based indexing**

**`F.arrays_zip(a, b)`**: Zip arrays into `ArrayType(StructType)` with fields `a` and `b`

**`F.zip_with(a, b, lambda x, y: expr)`**: Element-wise operation on two arrays

**`F.sequence(start, end)`**: Generate array from start to end (inclusive)

### 3.7 Null & Missing Value Handling

**`df.na.fill(value)`**: Fill null values

**`df.na.replace(['N/A', 'Unknown'], 'missing')`**: Replace specific string values (NOT nulls)

**`df.dropna(how='any', thresh=2, subset=['col1'])`**: Drop rows based on null criteria

### 3.8 Reading & Writing Delta

**`spark.read.format('delta').load('/path/to/delta')`**: Read Delta table

**`spark.read.table('table_name')`**: Read metastore-registered table

**Time Travel**:
```python
spark.read.format('delta').option('versionAsOf', 2).load(path)
spark.read.format('delta').option('timestampAsOf', '2024-01-01').load(path)
```

### 3.9 Observability & Diagnostics

**`df.observe('metric_name', F.count(lit(1)), F.sum('col'))`**:
- Attaches inline metrics to query execution
- Accessible via `QueryExecutionListener`
- Executed within the query (not as separate aggregation)

## Topic 4: Troubleshooting & Tuning (10% - Questions 71–80)

### 4.1 EXPLAIN Variants

**`df.explain()`** (default): Physical plan

**`df.explain('formatted')`**: Physical plan with readable layout, node IDs, subplans

**`df.explain('codegen')`**: Shows generated JVM source code from WholeStageCodegen

**`df.explain('cost')`**: Physical plan with cost estimates

### 4.2 Configuration at Runtime

**`spark.conf.set('spark.sql.shuffle.partitions', 50)`**: Set config during session

**`spark.conf.get('spark.sql.shuffle.partitions')`**: Read config value

### 4.3 Cost-Based Optimizer (CBO)

**Prerequisites**: Statistics must be collected via `ANALYZE TABLE table_name COMPUTE STATISTICS`

**Capability**: Reorder joins in multi-table queries to minimize intermediate result size

### 4.4 Adaptive Query Execution (AQE)

**`spark.sql.adaptive.enabled = true`** (default in Spark 3.2+)

**Features**:
- **Coalesce partitions**: Merge small partitions after shuffle
- **Skew join handling**: Detect and split skewed partitions
- **Join strategy switch**: Convert to BroadcastHashJoin at runtime if one side becomes small

**Skew Threshold**:
- `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes`: Size threshold above which a partition is "skewed"
- `spark.sql.adaptive.skewJoin.skewedPartitionFactor`: Multiplier for skew detection

### 4.5 Data Locality Tuning

**`spark.locality.wait`**:
- Time to wait before relaxing data locality requirements
- Higher values: Better data locality but may delay task launch
- Lower values: Faster scheduling but potentially worse locality

### 4.6 Compression

**`spark.shuffle.compress = true`** (default):
- Compresses shuffle output files to disk
- Uses `spark.io.compression.codec` (default `lz4`)
- Tradeoff: CPU for disk I/O reduction

**Default Codec**: `lz4` (fast, reasonable compression)

### 4.7 Executor Cores Tuning

**Optimal**: 4–5 cores per Executor

**Too High (16+ cores)**:
- Single HDFS client bottleneck (not designed for high concurrent threads)
- Increased GC pressure (one large JVM heap shared by many threads)
- Reduced HDFS throughput per task

**Too Low (1–2 cores)**:
- Reduced parallelism within Executor
- Underutilization of hardware

### 4.8 Skew Mitigation Strategies

**Salting**:
- Add random salt (0 to N-1) to large table's join key
- Replicate small table N times with each salt value
- Join on composite key (original key + salt)
- Aggregate afterward if needed

**AQE Skew Handling**: Enable `spark.sql.adaptive.skewJoin.enabled = true`

**Broadcasting**: If small table fits in memory, use `broadcast()` to convert SortMergeJoin to BroadcastHashJoin (avoids skew entirely)

**More Partitions**: Increasing `spark.sql.shuffle.partitions` spreads skew across more tasks (marginal benefit for single-key skew)

## Topic 5: Structured Streaming (10% - Questions 81–90)

### 5.1 Triggers & Processing Modes

**`trigger(processingTime='30 seconds')`**:
- New micro-batch every 30 seconds (or when previous finishes, whichever is later)
- Processes all data accumulated since last batch

**`trigger(once=True)`**:
- Single micro-batch; processes all available data; stops

**`trigger(availableNow=True)`**:
- Multiple micro-batches; processes all available data efficiently; stops

**`trigger(continuous='1 second')`** (experimental):
- Continuous Processing mode; runs without micro-batch boundaries
- Sub-millisecond latency; checkpoints asynchronously at specified interval

### 5.2 Source-Specific Options

**File Source**:
- `maxFilesPerTrigger`: Limit files processed per batch (rate control)

**Kafka Source**:
- `startingOffsets='earliest'`: Start from beginning if no checkpoint; resume from checkpoint on restart
- Supports offset management and exactly-once semantics

### 5.3 Stream-Static Join

**Supported**: Streaming DataFrame + static (batch) DataFrame

**Behavior**: Static DataFrame is re-read once per micro-batch; current snapshot is used

**Not Supported**: Both sides must not both be streaming unless using stream-stream join with state management

### 5.4 Streaming State Management

**`dropDuplicates()` Requirements**:
- Requires **watermark** to bound state size
- Watermark determines when dedup state is evicted
- Without watermark, state grows indefinitely

**`mapGroupsWithState` / `applyInPandasWithState`**:
- User-defined state per group key
- Watermark optional (can use processing-time timeouts)
- `mapGroupsWithState` emits exactly one row per group per batch
- `flatMapGroupsWithState` emits 0+ rows per group per batch
- State is automatically restored from checkpoint on restart

### 5.5 Streaming Progress Tracking

**`query.status`**: Current state dict (initialized, processing, waiting, etc.)

**`query.lastProgress`**: Metrics from most recently completed micro-batch (batch ID, input rows, processing time, etc.)

**`query.awaitTermination()`**: Block until query terminates

**`query.stop()`**: Stop the query

### 5.6 Streaming Limitations

**Global Sort (`orderBy`)**:
- NOT supported in Structured Streaming (unbounded stream)
- Raises `AnalysisException`

**Stateless operations** (filter, select):
- Can run in any output mode without watermark

## Topic 6: Spark Connect (5% - Questions 91–95)

### 6.1 Client Connection

**Connection Pattern**:
```python
spark = SparkSession.builder.remote('sc://hostname:15002').getOrCreate()
```

**Default Port**: 15002

### 6.2 Architecture

**Classic Spark**:
- Py4J socket bridge
- Driver embedded in application JVM

**Spark Connect (gRPC)**:
- Language-agnostic gRPC over HTTP/2
- Protocol Buffers for request serialization
- Apache Arrow for result batches
- Driver runs remotely on cluster
- Client crash ≠ job failure; client can reconnect

### 6.3 Plan Analysis & Execution

**Plan Analysis**: Happens on **server** when an action is triggered (e.g., `.count()`, `.show()`)

**Error Handling**: Analysis errors (missing columns, type mismatches) are raised on the client after being returned from server

### 6.4 Databricks Serverless

**Uses Spark Connect** as underlying protocol

**Key Points**:
- `SparkContext` and RDD API are **unavailable**
- Notebook process is isolated from Spark Driver (enables instant provisioning)
- Multi-language support (Python, Scala, SQL) via single Spark Connect server
- SQL hints: `spark.connect.ssl.enabled` for SSL/TLS configuration

### 6.5 Multi-Language Support

**Spark Connect API** is language-agnostic via gRPC

**Supported Clients**: Python, Scala, Go, Rust, Java (any language with gRPC client library)

**No JVM Required**: Client processes do not need a local JVM

## Topic 7: Pandas API on Spark (5% - Questions 96–100)

### 7.1 Core Operations

**`ps.merge(left, right, on='key', how='inner')`**: Join two pyspark.pandas DataFrames

**`ps.get_dummies(psdf, columns=['color'])`**: One-hot encoding; returns distributed pyspark.pandas DataFrame

**`ps.read_csv('s3://bucket/file.csv')`**: Cloud storage supported (delegates to Spark's file I/O)

### 7.2 Inter-DataFrame Operations

**`ps.set_option('compute.ops_on_diff_frames', True)`**:
- By default, operations between different pyspark.pandas DataFrames are disallowed (require implicit join)
- Enable this option to allow operations

**Example**:
```python
psdf1['a'] + psdf2['b']  # Raises error unless option is enabled
```

### 7.3 Compute Shortcuts

**`ps.set_option('compute.shortcut_limit', 1000)`**:
- DataFrames with ≤1000 rows are collected eagerly and cached locally
- Operations like `len()`, `head()` return instantly
- Larger DataFrames trigger full distributed Spark jobs

**Impact on `len()`**:
- Small DataFrame: Returns instantly from local cache
- Large DataFrame: Requires full Spark count job

### 7.4 Data Conversions

**`ps.from_pandas(pdf)`**: pandas → pyspark.pandas (distributed)

**`ps.from_spark(sdf)`**: PySpark DataFrame → pyspark.pandas (distributed)

**`psdf.to_spark()`**: pyspark.pandas → PySpark DataFrame (distributed)

**`psdf.to_pandas()`**: pyspark.pandas → pandas (collects all data to Driver; OOM risk!)

### 7.5 Index Types

**`distributed-sequence`** (default):
- Uses partition ID + offset within partition
- Unique globally; no shuffle required
- Non-strictly sequential (gaps between partitions)
- Fast and recommended

**`sequence`**:
- Strictly sequential integers (0, 1, 2, ...)
- Requires global sort (full shuffle)
- Expensive; only if strict ordering required
